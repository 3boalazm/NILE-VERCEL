# خطة التحقق المستقل من طلب تطوير NPF

- التاريخ: 2026-10-15 (UTC).
- خط الأساس: `67699401650da9222df15e922d57a0daaac12a0d`، الفرع `arena/2f247beb-npf`.
- السؤال الحالي: هل الطلب السابق له تقارير؟ وهل نُفّذ فعلًا؟ هذه مراجعة إثبات وليست إعادة تصميم عمياء.

## المنهج قبل التعديل

1. جرد التقارير المحلية وتاريخ Git والصفحات والمكونات والاختبارات.
2. البحث الموجّه في Google Drive/Docs وLinear عن وثائق NPF، دون استنتاج عدم وجودها من بحث واحد.
3. مصفوفة تربط كل مطلب بالدليل: منفذ / جزئي / غير منفذ / غير قابل للتحقق.
4. فحص الكود: بنية الموقع، التصميم والحركة، RTL/LTR، التنقل والشراء والحساب، الأمان والنشر وSEO والتحليلات.
5. محاولة تثبيت مطابق للقفل، ثم unit tests وlint وtypecheck وbuild؛ تسجيل المخرجات والقيود كما هي.
6. تشغيل واجهة ومتصفح إن توفرت المتطلبات. لا تُنسب قياسات Lighthouse أو مراجعة بصرية فعلية إلى مجرد قراءة كود أو HTML.
7. توثيق كل مسار تحليل في Markdown، مع أولويات وشروط قبول وخطة تنفيذ. لا تغيير للهوية أو حذف وظائف أو تعديل بيانات خارجية أثناء المراجعة.
8. نشر خلاصة جديدة في Docs إن أمكن، وربطها بسجل Linear مناسب فقط بعد اكتشاف المشروع/الفريق الصحيح؛ لا إنشاء تذاكر في فريق غير معروف ولا ادعاء مزامنة لم تحدث.

## البحث والمقارنة

- المصدر الأول: الكود الحالي ونتائج أوامر قابلة للتكرار، وليس ادعاءات التقارير القديمة.
- المصدر الثاني: تقارير الريبو وملف patch الموجود؛ تُراجع كوثائق تاريخية ولا يُطبّق patch آليًا.
- المصدر الثالث: وثائق الأدوات المثبتة وGitHub/السجلات المتاحة. الإنترنت المباشر مقيد لمضيفين محددين؛ أي benchmark تنافسي حي خارجهم غير متاح في هذه البيئة.
- لا نسب تحويل، تقييمات جودة رقمية، أو ادعاءات طبية جديدة دون بيانات وموافقات.

## حدود الدقة

الحالة المحلية لا تثبت نشر النسخة نفسها على الدومين. نجاح unit tests لا يثبت الدفع الحقيقي. تقرير قديم يذكر متصفحًا أو أرقام أداء بلا artifacts قابلة لإعادة التشغيل يُعامل كتاريخ غير متحقق حاليًا. كلمة native هنا تُراجع بمعنى كود ويب مملوك داخل الريبو؛ لا يُفترض أنها تعني React Native أو تطبيق موبايل أو HTML بلا إطار عمل.
